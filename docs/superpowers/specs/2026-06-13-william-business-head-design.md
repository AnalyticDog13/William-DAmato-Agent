# William D'Amato — Business Head pivot (owner builds the websites)

- **Date:** 2026-06-13
- **Status:** Approved design, pending spec review → implementation plan
- **Owner:** Powell

## 1. Context & motivation

Today William D'Amato runs the full sales-and-delivery pipeline *including*
building and deploying the websites himself (React/Framer Motion previews via
`buildPreviewSite`, a revision loop, and Vercel preview/production deploys of his
own artifact). The owner is taking over website creation. William's job becomes
**business head**: find leads, run Opus-personalized outreach, handle replies and
follow-ups, notify the owner, **advise** on the build by generating a full
website-build prompt for the owner to run on Fable 5 / Opus 4.8, and **ship** the
owner's finished repo plus write the delivery email.

The website-building capability is **preserved but silenced behind a default-off
flag**, with its side-effecting API calls (build + self-deploy) not executed while
off, so it can be re-enabled later.

## 2. Goals / non-goals

**Goals**
- William no longer builds or deploys his own website artifacts (default).
- On a positive reply, William produces a `WebsiteBrief` — a full build prompt
  (Three.js / GSAP / Framer Motion, animations, photos, real company info,
  recommended plugins) from the audit weaknesses + the lead's real scraped site.
- William includes a note in the website prompts to make the websites "awwward winning worthy"
- The owner builds the site externally, then marks it ready with a repo URL;
  William ships it (under `DEPLOY_PRODUCTION`) and drafts the delivery email.
- Outreach copy is generated by Opus (mock-first; real on `ANTHROPIC_API_KEY`).
- Everything works keyless today via mock adapters; `npm run demo` stays green.

**Non-goals**
- No new policy gates. No change to DNC/unsubscribe, the follow-up/close-out
  sequence, reply classification, billing, or reporting.
- No deletion of the builder code — it is flag-gated, not removed.
- Real repo-based Vercel deploy, real Firecrawl scraping, and real Opus calls are
  credential-gated (OwnerRequests); they simulate until keys arrive.

## 3. Locked decisions

1. **Off-switch:** a single config flag `WILLIAM_BUILDS_WEBSITES` (default
   `false`) — not literal code comments.
2. **Ship handoff:** dashboard "Website ready" action + pasted repo URL — not a
   GitHub webhook.
3. **Brief storage:** a new `WebsiteBrief` entity — not a field on `SiteProject`.
4. **Firecrawl scope:** a new adapter feeding the build-prompt only — the
   existing Playwright/http auditor is unchanged.

## 4. Architecture

### 4.1 The off-switch (`WILLIAM_BUILDS_WEBSITES`, default `false`)

- Add `williamBuildsWebsites: boolean` to `RuntimeConfig` in
  `packages/core/src/env.ts` (env `WILLIAM_BUILDS_WEBSITES`, default `false`).
- In `workers/orchestrator/src/pipelines.ts`, the four builder handlers —
  `handlePreviewBuild`, `handleSiteRevise`, `handleDeployPreview`,
  `handleDeployProduction` (William's own artifact) — early-return when the flag
  is off, writing an audit/activity note, and **never call `buildPreviewSite`,
  `applyRevisionOverrides`, or `vercel.deploy`**. This is how "API calls
  associated with that functionality are not used" is satisfied while leaving the
  code intact and type-checked.
- The positive-reply branch in `handleReply` enqueues `brief.generate` instead of
  `preview.build` when the flag is off.
- The dashboard endpoints `POST /api/site-projects/:id/revisions`,
  `/request-deploy`, and `/deploy-preview` are gated by the same flag (return a
  clear "builder disabled" response).
- The builder handlers stay registered in `JOB_HANDLERS` so any stale queued job
  no-ops safely instead of crashing.
- Flipping the flag to `true` restores today's builder pipeline unchanged.
  `.env.example` and CLAUDE.md document the re-enable steps.

### 4.2 New entity: `WebsiteBrief`

Standard entity path (CLAUDE.md): zod schema in `packages/core/src/schema/` →
repository in `packages/db` → collection whitelist in `apps/api/src/server.ts` →
dashboard page. Fields:

- `id`, `createdAt`, `updatedAt`
- `leadId`, `opportunityId`
- `websiteUrl` (the lead's current site)
- `weaknesses: string[]` (from the `WebsiteAudit`)
- `companyFacts` (services, hours, photos, about, contact — from Firecrawl)
- `buildPrompt: string` (the full generated prompt)
- `recommendedStack` (`libs`: Three.js / GSAP / Framer Motion …; `plugins`: …)
- `targetModel`: `"fable-5" | "opus-4-8"` (default `"fable-5"` for design quality)
- `generatedBy`: `"mock" | "opus-4-8" | "fable-5"`
- `repoUrl: string | null` (set when the owner marks the site ready)
- `status`: `"ready" | "shipped"`

### 4.3 New mock-first adapters (`packages/integrations`)

- **`firecrawl`** — `scrapeCompany(ticket, url) → CompanyFacts`. Mock synthesizes
  facts from the existing audit's extracted data (keyless/demo works); real
  implementation activates on `FIRECRAWL_API_KEY` (add to `.env.example`,
  `detectCredentials`, and `createIntegrations` in
  `packages/integrations/src/registry.ts`). It is a read/scrape → carried on an
  operational ticket (audited, ungated), and simulates on `ticket.dryRun` like
  every other adapter.
- **LLM adapter** — used for both build-prompt generation and Opus outreach
  personalization. Mock returns today's deterministic template output; real uses
  Opus 4.8 via the Anthropic SDK when `ANTHROPIC_API_KEY` is present. Selected by
  credential presence, mocks as fallback (existing pattern).
  - **Invariant 1 (load-bearing):** scraped site content and audit text enter the
    prompt strictly as *quoted material to transform*, never as instructions.
    This change MUST go through `compliance-reviewer` (text enters an LLM prompt).

### 4.4 New jobs (`workers/orchestrator/src/pipelines.ts`)

- **`brief.generate`** (replaces `preview.build` on positive reply when the flag
  is off): gather audit weaknesses → `firecrawl.scrapeCompany` → LLM build-prompt
  → insert `WebsiteBrief` (status `ready`) → owner-notification activity
  ("📋 Website brief ready — paste into Fable/Opus to build").
- **`site.ship`** (enqueued by the API when the owner submits "Website ready" +
  repo URL; requires a granted `DEPLOY_PRODUCTION` approval): record `repoUrl` on
  the `WebsiteBrief` (status `shipped`) → deploy the repo to Vercel production
  (dry-run now; real repo/git-source deploy is credential-gated, with an
  OwnerRequest) → `DeploymentRecord` → enqueue the delivery-email draft.

### 4.5 Outreach goes Opus

`createFirstTouchDraft` / `createFollowUpDraft` (`workers/outreach/src/draft.ts`)
source their copy from the LLM adapter (mock = current templates, real = Opus).
Output still passes `validateDraft` (opt-out line + compliance), still requires
owner approval, still feeds the variant/experiment system. The **delivery email**
after shipping is a new draft variant (e.g. `delivery-1`) that shares the live
link / offers a call, gated by `SEND_FIRST_TOUCH` (same outbound-email risk class
as follow-ups) and owner-approved.

### 4.6 Dashboard

- New **Website Briefs** page: shows each brief (copyable `buildPrompt`,
  `websiteUrl`, weaknesses, `targetModel`) and a **"Mark website ready"** action
  with a repo-URL field → triggers `site.ship`.
- The existing **Site Projects** page is kept but renders a "builder disabled"
  state while the flag is off.

## 5. What does NOT change

Policy engine + 8 gates; DNC/unsubscribe screening at intake/draft/send; the
no-response follow-up + 14-day close-out; reply classification + immediate
positive-reply owner notification; billing; reporting/memory. No new gates: ship
uses `DEPLOY_PRODUCTION`, the delivery email uses `SEND_FIRST_TOUCH`, and the
scrape + LLM calls are operational reads (audited, ungated; the *output* is gated
at draft approval / deploy approval).

## 6. New happy path (data flow)

1. Lead → audit → score → contact → **Opus draft (mock-first)** → owner approves →
   send → reply.
2. Positive reply → opportunity + owner notified → **`brief.generate`**:
   Firecrawl scrape (mock) + LLM build-prompt (mock) → `WebsiteBrief` (`ready`) →
   owner notified "brief ready."
3. Owner copies the brief into Fable/Opus, builds + reviews the site.
4. Owner clicks **"Website ready" + repo URL** → `DEPLOY_PRODUCTION` approval →
   **`site.ship`** (dry-run deploy now) → `DeploymentRecord` → **delivery-email
   draft** → owner approves → sent.
5. Follow-up and close-out machinery + notifications run alongside throughout.

## 7. Testing

Mock-first ⇒ suite stays green with zero keys; `npm run demo` shows the new path.

- **Unit:** flag-off no-ops the four builder handlers (assert no `buildPreviewSite`
  / `vercel.deploy` calls); positive reply enqueues `brief.generate` not
  `preview.build` when off; `WebsiteBrief` schema round-trip; brief-generator mock
  content (contains weaknesses, real facts, stack libs); Firecrawl mock; ship
  handler records repo + dry-run deploy + enqueues delivery draft; delivery draft
  passes `validateDraft`.
- **Integration:** positive-reply → brief pipeline; ship → deploy(dry-run) →
  delivery draft.
- **Preserved:** all policy/pipeline safety tests untouched. Existing builder
  tests are kept and run with `WILLIAM_BUILDS_WEBSITES=true` so the builder keeps
  coverage for when it is re-enabled.

## 8. Env & OwnerRequests

- `.env.example` gains: `WILLIAM_BUILDS_WEBSITES=false`, `ANTHROPIC_API_KEY=`,
  `FIRECRAWL_API_KEY=`.
- New OwnerRequests bootstrap for: the Anthropic key (real Opus outreach + real
  brief generation), the Firecrawl key (real scraping), and Vercel repo/git-source
  deploy (real shipping).

## 9. Deferred / credential-gated

- Real Firecrawl scraping (mock until `FIRECRAWL_API_KEY`).
- Real Opus calls for outreach + brief (mock until `ANTHROPIC_API_KEY`).
- GitHub-webhook ship trigger (out of scope; dashboard action chosen instead).

## 10. Owner-overridable calls already made

- `WebsiteBrief.targetModel` defaults to recommending **Fable 5**.
